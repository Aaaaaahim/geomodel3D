# 一、P1 必修（与设计不符 / 影响核心流程正确性）

## P1-1 DSI 插值"空转"：界面可选但算法静默降级为 IDW

### 位置
- `geomodel3d/config/schema.py:72`
- `geomodel3d/ui/widgets/parameter_panel.py:119`
- `geomodel3d/engine/layered.py:95-116`

### 问题描述

设计文档 6.1《插值算法选型矩阵》将 **DSI（离散光滑插值）** 列为 OpenGeode 高精度建模的核心算法，并给出工程建议"正式建模 = 协同克里金或 DSI"。`InterpConfig.method` 的合法值白名单也包含 `dsi` 与 `gempy`：

```python
allowed = {"cokriging", "kriging", "idw", "dsi", "gempy"}
```

参数面板同样把 `dsi` 放进了下拉选项，用户可以在界面中直接选择"DSI"。

但是，真正执行插值分派的 `engine/layered.py:_interface_surfaces` 只特判了两个方法：

```python
if method == "cokriging" and spec.seismic and len(pts) >= 4:
    est = _cokrige_interface(...)
elif method in ("kriging", "cokriging") and len(pts) >= 4:
    est = kriging(...)
else:
    est = idw(pts, vals, xy, ...)   # ← method == "dsi"/"gempy" 会走到这里
```

即：**用户选择 DSI（或 gempy 插值），实际得到的是 IDW 的结果**，没有任何提示或日志。

### 影响

1. 用户以为用了高精度 DSI 插值，得到的却是反距离加权结果，**模型结果与用户预期不符**，属于静默的错误输出。
2. 违背设计文档 6.1 的核心算法承诺，无法支撑"正式建模 = DSI"的工程建议。
3. 由于 IDW 不满足地质光滑性与断层断距约束，矿体界面质量下降，进而影响储量计算、剖面生成的正确性。

### 修复建议

二选一，推荐 A：

- **A（推荐，最小改动且诚实）**：把 `dsi` / `gempy` 从可选方法中移除，或在 `_interface_surfaces` 中遇到未实现方法时抛出 `GeoModelError(MDL_IPL_002)` 或至少发布一条 WARNING 事件告知用户"已回退 IDW"，而不是静默降级。
- **B（完整实现）**：在 `algorithms/interpolation.py` 中按设计 6.1 实现 DSI 光滑插值（光滑权 + 硬约束 + 断距约束的最小二乘求解），并在 `layered.py` 中接入 `dsi` 分支，配套单元测试与回归基准。

## P1-2 夹石剔除（BR-04）未实现：指标已定义但算法从未使用

### 位置
- `geomodel3d/domain/reserve.py:27`
- `geomodel3d/config/schema.py:91`
- `geomodel3d/algorithms/reserve.py:156-165`

### 问题描述

业务规则 **BR-04** 明确要求："储量计算前必须通过'工业指标+可采范围'双校验：**厚度 < 最小可采厚度的夹层剔除规则**；低品位段是否可并入邻段（米-克/吨规则可配置）。"

指标模型 `ReserveMetrics` 与工程配置 `ReserveConfig` 均已定义夹石剔除厚度字段：

```python
# domain/reserve.py:27
max_waste_thickness: float = Field(default=0.0, ge=0.0, description="夹石剔除厚度 m")
```

但储量算法的唯一筛选入口 `_apply_indicators` 只实现了两个条件：

```python
def _apply_indicators(idx, grades, thickness, metrics):
    mask = (grades[idx] >= metrics.cutoff_grade) & (thickness[idx] >= metrics.min_thickness)
    return idx[mask]
```

`max_waste_thickness` **从未参与任何计算**，块段法的"夹石剔除后块段可采性判定"同样缺失（`_block_aggregate` 只按块平均品位/厚度重查一次）。

### 影响

1. 含夹石（废石夹层）的矿体储量被**系统性高估**：夹石段计入矿量，金属量与矿石量偏大。
2. 直接违反 BR-04，储量报告无法通过"指标双校验"，也缺少"米-克/吨规则可配置"的能力（该能力同样未实现）。
3. 影响 R5 风险（储量结果口径分歧）——用户按规范设置了夹石剔除参数，结果却未体现，导致结果不可信。

### 修复建议

在 `algorithms/reserve.py` 中实现夹层剔除逻辑：

- 块段法：对块内单元按深度序游走，识别连续"废石夹层"（品位 < 边界品位 且 厚度 ≥ `max_waste_thickness`）并将其从块段中剥离；被剥离部分不参与体积/矿量累计。
- 体积法：同样按"夹层段"过滤，或对每个连续采段判定"段内夹石累计厚度是否超过阈值"。
- 补充 BR-04 的"米-克/吨当量合并规则"配置项（可暂缓，但需在报告中标注未支持）。
- 增加覆盖 `max_waste_thickness` 的单元测试（含夹层场景、不满足阈值场景）。

## P1-3 地震层位 CRS 未纳入坐标归一：跨投影数据会被错误变换

### 位置
- `geomodel3d/domain/entities.py:121`
- `geomodel3d/services/data_service.py:116-145`

### 问题描述

`SeismicLayer` 定义了独立的源坐标系字段：

```python
# domain/entities.py:121
source_crs_epsg: Optional[int] = None
```

设计文档 4.2 要求"记录'源 CRS→目标 CRS'链"、8.5 要求每个数据源保留可逆变换链。但 `DataService.unify_crs` 实现时**忽略了该字段**，只用工程级 `project.config.project.source_crs` 一把梭地把所有数据变换到目标 CRS：

```python
def unify_crs(self, target=None):
    source = project.config.project.source_crs      # 工程级单一源 CRS
    ...
    for layer in project.seismic:
        layer.points = self._crs.transform_points(points, source, target).tolist()
```

同时，`seismic_io.py` 的 Esri ASCII / SEG-Y / 点云解析都**没有把数据源 CRS 写入 `layer.source_crs_epsg`**。

### 影响

1. 若 SEG-Y 道头坐标、栅格角点坐标与钻孔采用的投影不同（实测中很常见，例如 SEG-Y 用经纬度、钻孔用 UTM），`unify_crs` 会按钻孔的源 CRS 去解释地震坐标，**变换结果完全错误**，模型融合（协同克里金趋势约束）失效。
2. 违背 8.5"源→目标变换链"与 4.2 的 CRS 归一流程。
3. 导出成果坐标错误，直接污染下游 QGIS/CAD 成果。

### 修复建议

1. 在 `seismic_io.py` 各类解析器（`read_esri_ascii_grid` / `read_segy` / `_read_point_cloud`）中把已知的源 CRS 写入 `layer.source_crs_epsg`（SEG-Y 道头坐标尺度信息可辅助判断）。
2. 在 `unify_crs` 中改为**逐数据源变换**：钻孔/断层用工程级 source_crs，地震层位用 `layer.source_crs_epsg`（为空时回退工程级，并发布 WARNING）。
3. 增加跨投影（如 EPSG:4326 地震 + EPSG:32650 钻孔）的集成测试。

## P1-4 默认包围盒与真实坐标不匹配：越界钻孔仅告警仍可建模，产出无意义模型

### 位置
- `geomodel3d/config/schema.py:42-43`
- `geomodel3d/domain/rules.py:91`
- `geomodel3d/services/data_service.py:64-69`

### 问题描述

新建工程的默认包围盒为 `[0,0,-1000] ~ [1000,1000,0]`：

```python
min: List[float] = Field(default_factory=lambda: [0.0, 0.0, -1000.0], ...)
max: List[float] = Field(default_factory=lambda: [1000.0, 1000.0, 0.0], ...)
```

规则引擎对孔口坐标越界的判定只是 WARNING（不阻断）：

```python
# domain/rules.py:91
report.add(Severity.WARNING, "DAT-VAL-BND", f"钻孔 {hole.hole_id} 孔口平面坐标越界", hole.hole_id)
```

于是：用户直接导入 UTM 坐标（例如 x≈499000，见 `examples/demo/job.json` 的 bounds 即真实 UTM），钻孔全部落在默认包围盒之外，校验仍通过（WARNING 不阻断），进入建模后：

- `layered.py:_interface_samples` 收集到的界面点在网格之外；
- `_interface_surfaces` 在网格中心处 k 近邻插值**找不到任何样本**（或距离极远），落入 `fallback = zmax + (zmin - zmax) * (index / n_layers)` 的占位平面；
- 最终产出的是**规则占位分层模型，与钻孔数据完全无关**，而界面无任何报错。

### 影响

1. 核心流程"导入 → 建模"看似成功，实则是退化占位结果，**模型与数据毫无关系**，属于最危险的静默失败。
2. 用户在 UI 中看到"建模完成（N 单元）"却没有意识到 bounds 错误，后续储量/剖面全部基于错误模型。

### 修复建议

- **首选**：`import_boreholes` 校验前，若钻孔坐标明显超出工程 bounds（如 >99% 孔口越界），按钻孔范围自动重设 `project.config.project.bounds`（留边 10%），并发布提示事件。
- 或：把 DAT-VAL-BND 升级为 ERROR（阻断），并提示用户设置正确 bounds / 重选 CRS。
- 同时建议在 UI 导入向导增加"自动计算工程范围"选项。

# 二、P2 建议（设计文档明确但未落地 / 工程化改进）

## P2-1 长任务开始不自动建立版本快照

### 位置
- `geomodel3d/services/modeling_service.py:71-104`（create_run）
- 设计文档 3.6

### 详细阐述

设计 3.6 规定："长任务开始时自动建立版本快照（可回滚）；结束时广播 `ModelChanged` 事件。"当前实现只有：

- 手动快照（`ProjectService.snapshot`，Ctrl+Shift+N / 版本历史对话框）；
- 定时自动保存（`autosave`，仅落盘 `.autosave` 文件）。

`create_run` / `rebuild_local` **不会在开始前自动建立内存快照**。因此用户点击"快速建模"或"应用并重建模"时，如果建模失败、被取消（`TaskCancelled`）或参数回退（引擎不可用时回退 Mock），**当前模型已处于中间/失败状态**，Undo 栈只覆盖断层参数（`fault_params` 一类），无法回滚到任务前的一致模型。

### 影响

- 违背 BR-08"取消后回到最近一致状态（通过版本快照回滚）"。
- 建模被取消或失败后，工程停留在不可预期的状态。

### 修复建议

在 `ModelingService.create_run` / `rebuild_local` 提交后台任务前，对当前 mesh 做一次 `capture(...)`（复用 `domain/snapshot.py`，kind="model"），任务失败/取消时由调用方调用 `restore_snapshot` 回滚，或至少把自动快照推入 `project.snapshots`。

## P2-2 OpenGeode 能力声明与实现不符：`fault_cut=True` 但拓扑切割未实现

### 位置
- `geomodel3d/engine/opengeode_engine.py:113-120`
- 设计文档 4.3.1

### 详细阐述

`OpenGeodeEngine.capabilities` 声明：

```python
capabilities = EngineCapabilities(
    name="opengeode",
    high_precision=True,
    fault_cut=True,        # ← 声明支持断层切割
    closed_solids=True,
    ...
)
```

但该引擎实际只做：分层体元建模（复用 `build_layered_mesh`）→ 构造 `HybridSolid3D` → 计算邻接 → 写 `layer` 属性。断层落差**仅以分层阶段的 z 位移方式体现**，没有基于 OpenGeode 的拓扑级布尔切割。文件头 docstring 也自述：

> "OpenGeode-core 本身不含布尔切割算子（需额外的 geode/simplex 扩展），拓扑级切割列为后续工作。"

`fault_cut=True` 会让 UI/调度（`EngineRegistry.describe_all`、`decide_engine`）与用户误以为 OpenGeode 具备高精度断层切割能力。

### 影响

- 能力声明不诚实，误导功能展示与引擎调度决策。
- 复杂断层的上下盘错动边界粗糙（位移式近似），达不到"高精度断层切割"的商用预期。

### 修复建议

- 短期：把 `fault_cut` 改为 `False`，或拆分为 `fault_displacement=True` + `fault_boolean_cut=False`，如实声明。
- 中期：接入 geode/simplex 扩展实现真布尔切割，并在 `rebuild_local` 中利用拓扑切割重算影响域。

## P2-3 网格修复覆盖面不足：仅焊接/去退化/去重/光顺

### 位置
- `geomodel3d/algorithms/repair.py:48-93`
- 设计文档 5.6（M6）

### 详细阐述

设计 M6 定义的缺陷类型：尖灭处理（M6-F1）、空洞修补（M6-F2）、网格整形/锯齿（M6-F3）、简化（M6-F4）、超覆/退覆识别（M6-F5）、体检报告（M6-F6）。`algorithms/repair.py` 实际实现：

1. 顶点焊接（`_weld_vertices`，容差并查集）；
2. 退化单元剔除（`_filter_degenerate`）；
3. 重复单元剔除（`_filter_duplicate`）；
4. 拉普拉斯光顺（`_smooth`，边界固定）。

**空洞修补、尖灭处理、网格简化、超覆/退覆识别均未实现。** BR-09"导出前拓扑体检：非流形边、重复面、空洞、法向一致性；不合格给出修复建议或强制修复"——体检（`mesh_health.py`）已实现流形/边界检测，但"强制修复"只有上述四步，非流形与自交问题修复缺失。

### 影响

- 复杂拓扑（如布尔切割产生的非流形边、内部空洞）无法被自动修复，导出被 BR-09 检查单阻断却无修复路径。
- 尖灭/超覆等地质意义上的缺陷无处理手段。

### 修复建议

- 优先补：孔洞检测（边界环搜索）+ 三角剖分修补、非流形边的局部重网格化。
- 中期补：边塌缩简化（误差界 ≤ 容差）。
- 尖灭/超覆/退覆需要地质语义层处理（界面裁剪+重缝合），可列为独立里程碑，但至少要在 `health_check` 中给出检测项。

## P2-4 `_lith_to_mesh` 逐单元 Python 循环：5×10⁶ 单元性能隐患

### 位置
- `geomodel3d/engine/gempy_adapter.py:341-367`（尤其 351 行）

### 详细阐述

```python
codes = np.array([order_to_code.get(int(i), "UNK") for i in layer_index], dtype=object)
```

`layer_index` 是 `lith_block` 展平后的 `(nx*ny*nz,)` 数组，规模可达 **5×10⁶**（设计 2.3 规模上限）。该列表推导对每个单元执行一次 Python 层 get，违反设计 6.6"NumPy 连续数组 + 预排序"与"多分辨率缓存"性能策略。

### 影响

- 大分辨率下 GemPy 结果转 UMesh 阶段出现可感知的秒级停顿，卡在 UI 后台任务（虽不阻塞界面，但拖慢整个建模链路）。
- 违背 NFR 性能指标（10⁶ 单元交互 ≥25FPS、建模 ≤5s 量级）。

### 修复建议

向量化映射（两种均可）：

```python
# 方案一：pandas map / np.frompyfunc
from numpy import frompyfunc
mapper = np.frompyfunc(order_to_code.get, 1, 1)
codes = mapper(layer_index.astype(np.int64))

# 方案二：构造索引数组（层号不连续时先重映射）
unique = np.unique(layer_index)
remap = {int(v): order_to_code.get(int(v), "UNK") for v in unique}
codes = np.array([remap[v] for v in np.unique(layer_index)], dtype=object)[
    np.searchsorted(np.unique(layer_index), layer_index)
]
```

`layered.py:55` 的 `codes = np.array([order_to_code.get(int(o), "UNK") for o in layer_index], dtype=object)` 同样适用此优化（局部重建模也复用它）。

## P2-5 `export_dxf` 图层命名语义错误：把过滤列表当布尔用

### 位置
- `geomodel3d/dataio/exporters.py:147`

### 详细阐述

```python
name = layer_name(code, "ORE" if result.plan.show_layers else "GEOL")
```

`SectionPlan.show_layers` 是**图层过滤列表**（`build_section` 中 `show = set(plan.show_layers)`，空列表表示显示全部图层），而这里把它当作布尔标志：

- `show_layers` 为空（= 显示全部）→ 所有图层命名 `GEOL_<code>`；
- `show_layers` 非空（= 只显示部分）→ 所有图层命名 `ORE_<code>`。

与设计 8.6 命名规范"`GEOL_<stratum>`（地层）、`ORE_<body>`（矿体）按元素类别区分"不符——矿体层与普通地层在 DXF 中被混为一谈。

### 影响

- DXF 图层规范被破坏，CAD 一键图层管理失效。
- 埋下隐患：该错误还依赖了 `show_layers` 语义上恰好非空/为空的巧合。

### 修复建议

按元素类别显式区分：

```python
is_ore = code in result.plan.show_layers or code in _ORE_LAYERS
name = layer_name(code, "ORE" if is_ore else "GEOL")
```

（或引入明确的 `SectionPlan.layer_kinds` 映射，明确每个 code 的类别。）

## P2-6 事件订阅不完整 / 重复弹错：RUN_STARTED 未订阅，错误可能二次弹出

### 位置
- `geomodel3d/ui/main_window.py:289-304`（_on_event 分发表）
- `geomodel3d/services/modeling_service.py:165-180`（RUN_FAILED 发布）

### 详细阐述

1. `_on_event` 分发表**没有订阅 `RUN_STARTED`**（`events.py:26` 已定义、modeling_service 已发布）。异步任务的进度条要等第一条 `RUN_PROGRESS`（通常来自引擎 `ctx.progress(2/5/...)`）才显示，任务排队阶段用户无任何反馈。
2. 同步链路存在重复弹错的**潜在路径（需确认）**：`MainWindow._guard` 捕获异常弹 `ErrorDialog`；而 `modeling_service._execute` 失败时同时 `publish(RUN_FAILED)`，若 UI 之后又订阅了 RUN_FAILED 处理，则会二次弹窗。当前 `RUN_FAILED` 虽已订阅（`_on_run_failed`），但异步失败时 `_guard` 不捕获（异常在 worker 线程），只有一次弹窗，路径尚可；但 `jobs` 或同步 `async_run=False` 调用下需复核。

### 影响

- 用户体验：排队期无进度反馈；存在错误信息重复/混乱的隐患。

### 修复建议

- 订阅 `RUN_STARTED`：在分发表中加入 `RUN_STARTED: self._on_run_started`，进入运行态即显示进度条与"排队/启动中"状态。
- 统一错误出口：`RUN_FAILED` 事件只负责异步链路；`_guard` 负责同步链路；二者互斥，避免同一错误弹两次。补充一次同步+异步混合调用的 UI 冒烟测试。

# 七、用户实测问题修复（2026-09-10 追加）

**现象**：建模后"总是显示一个长方体，钻孔数据无影响"。

# 八、建模性能修复（2026-09-10 追加）

**现象**：导入起伏较大的钻孔（25 孔）后，48×48×32 网格建模耗时约 **244 秒**，用户以为"没反应/区别不大"。

**根因**：`engine/layered._interface_surfaces` 在**全部三维单元中心**（`nx·ny·nz`）上插值界面，而同一 `(i,j)` 列的所有单元 XY 完全相同，造成 `nz` 倍冗余。25 孔时单次建模产生 13824 次克里金线性求解（本应 1152 次）。

**修复**：先对查询 XY 去重（`np.unique(axis=0)`），仅在 `nx·ny` 个唯一列上插值，再按逆映射还原到单元。结果不变。

**效果**（起伏数据，`method=cokriging`）：
| 分辨率 | 修复前 | 修复后 |
| --- | --- | --- |
| 24×24×12 | 26.5 s | **2.2 s** |
| 48×48×32 | 243.5 s | **7.4 s** |
| 80×80×40 | — | **20.7 s** |

**回归用例**：`test_interface_interpolation_dedupes_xy`（断言插值点数为唯一 XY 列数而非单元数）。全量 **179 passed, 1 skipped**。

**附**：新增起伏测试数据 `examples/relief/boreholes.csv`（25 孔、2km×2km，N2 界面起伏约 281 m、K1 约 218 m），供导入验证。

# 十二、模型修复卡死修复（2026-09-10 追加）

**现象**：点击"自动修复"后进程阻塞、程序失败。

**根因**：
1. `algorithms/repair.py:_filter_degenerate` 对**每个单元**调用 `_polyhedron_volume`（Python 循环 + 每个面片创建 NumPy 数组）。48³（73728 单元）实测 **42.7s**，且运行在 UI 主线程 → 界面"无响应"。
2. `_fix_normals` 同样逐单元调用 `_signed_jacobian`。

**修复**：
1. `_filter_degenerate` 增加**向量化快路径**：同位数的单元一次性批量计算体积（复用 `umesh._tet_volumes_batch` / `_tetra_volumes_batch`），并用 `np.diff(np.sort(conn))==0` 向量化检测重复顶点；仅非均匀网格回退逐单元。
2. `_fix_normals` 向量化计算雅可比行列式，仅对负值单元翻转。
3. `RepairService` 增加 `tasks` 与 `async_run`：GUI 通过 `TaskManager` **后台线程**修复，进度条提示，完成后经 `MODEL_CHANGED` 刷新；`RepairService.repair(async_run=True)` 无任务管理器时自动同步回退（headless）。
4. `main_window` 连接 `taskFinished/taskFailed`（仅处理 `repair-*`），完成/失败更新状态或弹错。

**效果**：默认修复 48³ **42.7s → 2.35s**（80³ 8.5s）；界面不再阻塞。

## 13.2 自动纵向放大上限过低（10）→ 大面积薄层显示扁平

## 13.3 各界面独立插值相互穿插（层厚为负）

# 十五、坐标轴文字被纵向放大成"巨字"修复（2026-09-10 追加）

**现象**：快速建模后模型上的文字（坐标轴标签）非常大、显示不正常。

**根因**：`viewport` 原本 `show_bounds` 使用默认 `use_3d_text=True`（三维挤出文字），随后 `set_scale(zscale=...)` 会**缩放整个坐标轴 actor**。自动纵向放大对大范围薄层数据可达数十倍（如 Kansas 约 50×），三维文字在 Z 向被拉伸 50 倍 → 呈"巨字"。

**修复**：
- `show_bounds`/剖切路径统一改用 **2D 屏幕空间文字**（`use_3d_text=False, font_size=10`），不再随 `set_scale` 拉伸；三维轴框仍随纵向放大与模型一致。
- 图例在 `set_scale` 之后添加，同样不受缩放影响。

**验证**：真实 VTK 离屏渲染 + 假 plotter 断言 `show_bounds(use_3d_text=False)`。全量 **~189 passed, 1 skipped**；冻结包重建并自检 exit 0。

# 十六、中文地层代码导致视口崩溃修复（2026-09-10 追加）

**现象**：导入含**中文地层代码**的钻孔（如 Kansas 的"覆盖层/粘土层…"）后建模，模型改变触发重绘时崩溃：
`ValueError: String array contains non-ASCII characters that are not supported by VTK`。

**根因**：视口为支持拾取，把地层代码字符串写入 VTK 单元属性 `cell_data["layer"] = [str(code)]`。VTK 字符串数组仅支持 ASCII，中文代码直接报错。

**修复**：改为写**数值 id**——`_register_pick(label, kind)` 维护 `id↔(标签, 类别)` 映射，单元属性写入整数 `pick_id`；`_on_pick` 由 id 反查标签/类别（钻孔/断层/地层）。所有模式（层实体、体元、等值面、孔轨迹、断层线）统一改用数值 id；每次渲染重建映射表。

**验证**：Kansas（中文 5 层）真实 VTK 离屏渲染通过；全量 **~189 passed, 1 skipped**；冻结包重建并自检 exit 0。
